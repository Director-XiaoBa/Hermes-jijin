# 多轮验证工作流教训（09-02）

## 问题
完成系统改动后，只做了语法检查和文件存在性检查，用户追问"这些里面细节和逻辑有挨个具体的检查吗"——才发现我们只验证了"能不能跑"，没验证"跑出来的对不对"。

## 根因
验证流程缺少"数据质量"层面的检查。语法通过≠逻辑正确≠数据正确。

## 正确的验证流程（6轮递进）

### 第1轮：语法检查
```bash
python3 -m py_compile <script>
```

### 第2轮：文件完整性
- 脚本数量是否正确
- MySQL表是否存在且有数据
- Cron任务数量是否正确

### 第3轮：导入关系
- 检查所有import的模块是否存在
- 检查Skill中的脚本引用是否都有效
- 检查Cron prompt中引用的脚本是否都存在

### 第4轮：核心脚本运行
```bash
# 逐个运行核心脚本，检查输出
python3 fund_data_collector.py  # 检查8/8源成功
python3 position_manager.py summary  # 检查持仓数据
python3 pre_trade_check.py 025209 buy  # 检查检查清单
```

### 第5轮：数据质量检查（最容易遗漏）
```python
# 检查实际输出的数据是否合理
# 例：NAV=0？RSI=None？止损=0？重复记录？
```

### 第6轮：业务逻辑检查
- 预测验证率是否正常（15%太低）
- 止损距离是否合理（1.3%太近）
- 板块匹配是否准确（模糊匹配成功率）

## 本次发现的真实bug（通过第5-6轮发现）

| bug | 严重度 | 通过哪轮发现 |
|-----|--------|-------------|
| 部分基金RSI=None | 高 | 第5轮（数据质量） |
| 同基金多条记录 | 中 | 第5轮（数据质量） |
| 预测验证率15% | 中 | 第6轮（业务逻辑） |
| 板块匹配全部失败 | 中 | 第6轮（业务逻辑） |

## 关键教训
**用户不接受"应该没问题"——要看到验证输出才放心。验证不是走形式，是发现真正bug的唯一途径。**
